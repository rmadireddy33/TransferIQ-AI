## Actual API contract and graph

The manual trigger is named `StartTransferInvestigation`. Its input is `transferId` (string), for example `TRF-1002`. `ValidateInput` rejects blanks, path separators, whitespace, and values beyond 64 characters before any HTTP call.

| Node | Actual request or responsibility |
|---|---|
| BackendConfigured / ValidateBackendConfiguration | Fail closed until an HTTPS backend and secure HTTP connection are configured |
| GetTransferDetails | `GET /api/transfers/{transferId}`; validate 200 and required IDs; preserve actual `status` field |
| GetDeliveringPositions | `GET /api/delivering/accounts/{sourceAccountId}/positions?limit=100&offset=0`; account ID from transfer response |
| GetReceivingPositions | `GET /api/receiving/accounts/{destinationAccountId}/positions?transferId={transferId}&limit=100&offset=0` |
| RunReconciliation | `POST /api/transfers/{transferId}/reconcile`, JSON `{}`; accept 200 reused result or 201 new result |
| NormalizeReconciliation | Validate parsed HTTP `output.body`, execution status, counters, classifications, exception ownership and evidence; preserve Decimal strings |
| NormalizationFailed | Reject malformed responses before the business decision |
| RequiresInvestigation | `NormalizeReconciliation.output.unresolvedCount > 0` |
| CleanReconciliation / InvestigationRequired | Separate completion paths returning `result` |
| Failure terminals | Invalid input/configuration, per-HTTP failures, per-context validation failures and malformed reconciliation |

`ValidateTransfer`, `ValidateDeliveringPositions` and `ValidateReceivingPositions` run immediately after their HTTP nodes. The installed designer declares the HTTP status as `code`; SDK 6.66.5 documents `statusCode`. The validators support both, preferring `code`, and reject missing/non-success statuses. Both envelopes have contract coverage. A missing source account or empty source snapshot fails. Empty receiving staging reaches the deterministic engine, which identifies missing securities. Staging must carry `positionKind: RECEIVING_TRANSFER_STAGING` and `settledHoldings: false`.

The current context-fetch increment supports at most **100 records per side**. If `total` differs from the returned item count, it fails; it never silently drops later pages. Add paging before using larger accounts. Reconciliation itself remains authoritative and reads its own database transaction; the earlier GET results are context previews and are not a cross-request atomic snapshot.

Actual backend fields map as follows:

| Backend | Normalized result |
|---|---|
| `transferId` | `transferId` |
| `reconciliationRunId` | `reconciliationRunId` |
| `summary.totalPositions` | `totalPositions` |
| `summary.directlyMatched` | `directlyMatched` |
| `summary.evidenceExplained` | `evidenceExplained` |
| `summary.unresolved` | `unresolvedCount` |
| `summary.costBasisIssues` | Separate `costBasisIssues`, `costBasisExceptions`, `requiresCostBasisReview` |
| `exceptions` | Preserved full exception details; additional unresolved-only list |
| Position/exception `evidenceReferences` | Deduplicated evidence reference list |
| Transfer `status` | Preserved in transfer context and exposed as normalized `transferStatus` |

The declared Flow output is one object named **`result`**, containing all requested fields. It includes affected internal `securityId` values, exception classifications, an explanation, context positions, and transfer/run correlation. It does not invent a CUSIP or external security identifier. A `FAILED` result uses null counts, never a misleading zero or CLEAN default. HTTP failure summaries omit raw bodies, messages and headers; status and failing node provide correlation. The successful path also has a generated request correlation ID. The backend currently does not persist the custom HTTP correlation header; persisted `reconciliationRunId` is the durable link.

**CLEAN is quantity reconciliation only.** As specified, the decision uses quantity `unresolvedCount`. TRF-1004 therefore returns CLEAN with `costBasisIssues=1` and `requiresCostBasisReview=true`; it is not financially complete or ready for settlement. No workflow path updates custody, corrects a quantity, changes transfer status, or initiates settlement. IXP, agents and approval forms are absent.

## Secure configuration for a future cloud run

The committed artifact contains no credential, tenant ID, fabricated connection ID or hardcoded transfer ID. With no local binding files, compilation produces unbound managed HTTP nodes and sets `backendConnectionConfigured=false`. Execution returns `FAILED / CONFIGURATION_REQUIRED` before those nodes. This is a configuration guard, not simulated success.

To enable real cloud calls:

1. Host the existing backend at its actual Railway HTTPS address in a later deployment step. `localhost:8000` on Windows is reachable by local tests, not by UiPath Cloud. This task did not deploy or introduce a tunnel.
2. In the intended UiPath tenant/folder, create an Integration Service **HTTP** connection, named for example `TransferIQ API`. Select **API Key**, enter the HTTPS base URL, parameter name **`X-API-Key`**, add to **Header**, and enter the backend secret in the connection's secure Value field. For authentication validation use **`/api/corporate-actions?limit=1`**, which is protected; `/health` is public and cannot validate credentials. This matches [UiPath's HTTP authentication contract](https://docs.uipath.com/integration-service/automation-cloud/latest/user-guide/uipath-uipath-http-authentication).
3. Ensure the runtime identity can use the connection and Maestro Automate in that folder. Sign in using `uip login` in your own terminal if needed. Verify `uip login status --output json`.
4. List HTTP connections, then bind the selected real connection. The helper verifies Enabled state and pings it, derives its folder from the same returned record, and writes ignored local binding/config files. It never accepts or writes a secret.

```powershell
Set-Location C:\Projects\TransferIQ-AI
uip is connections list uipath-uipath-http --all-folders --refresh --output json
# Supply the actual hosted URL and the ID returned by the listing; these prompts contain no API key.

$connectionId = Read-Host 'Selected HTTP connection ID from the listing'
.\scripts\configure-maestro.ps1 -BackendBaseUrl $backendUrl -ConnectionId $connectionId
.\scripts\build-maestro.ps1
```

The helper could not be exercised against an actual connection because none exists. Its PowerShell syntax was checked. Recompilation resolves symbolic `transferiqHttp` and `transferiqFolder` through `.flow-sdk/bindings.json`, selects connector authentication, and uses paths relative to the connection's configured base URL. **The connection's base URL controls routing**; keep it equal to `.flow-sdk/runtime.local.json`'s `backendBaseUrl`. Changing the Flow variable alone does not retarget a managed connection. No secret should be put in a Flow input, plain variable, file, request header expression or command line.

The checked-in default URL is `http://localhost:8000` for local context. Local test tools accept `--base-url`. Cloud-connected builds require HTTPS. `.flow-sdk/bindings.json` and `runtime.local.json` are ignored; a configured generated `.flow` will contain tenant resource references, so review it before committing and rebuild the unbound artifact when sharing a tenant-neutral example.

## Errors and retries

All four managed HTTP nodes have `PT30S` timeouts and `retryCount=1` (at most two attempts). SDK documentation defines retryable failures as network failures, 429 and 5xx. Unauthorized/not-found/invalid requests take distinct failure exits without unlimited retries. This policy and graph routing are locally tested; UiPath's actual scheduling and error-envelope delivery still require a hosted runtime test.

Reconciliation retries use the backend's existing input fingerprint deduplication. Unchanged inputs reuse the same persisted result; changed inputs legitimately create a new historical run. No Idempotency-Key is invented for this endpoint. Timeouts produce FAILED, and a later retry can recover the persisted result without financial corrections.

Product validation reports **Valid with four reviewed EXPRESSION_DIAGNOSTIC warnings**, one for each HTTP failure terminal. The builder's supported `err(step, 'status')` emits a managed HTTP error read under `step.output`; the product validator types it only as `step.error`. The installed SDK skill explicitly documents this exception. Source check and compile have zero errors/warnings. These are not evidence of live runtime behavior. Transient registry fetch warnings also occurred; these Flow nodes are built-in types and no IXP/agent nodes are used.
