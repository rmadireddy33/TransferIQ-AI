# Step 9 API contracts

Base URL: `https://transferiq-api.onrender.com`. These routes are implemented locally; deployment was not present in the observed production check. All writes below are **isolated fictional demo dispositions**, not financial corrections. Existing private and Step 5 contracts remain unchanged.

## Routes

`R = /api/demo/runs/{runId}` and `P = R/resolution-plans/{planId}`.

| Method/path | Authorization / behavior |
|---|---|
| POST `/api/demo/runs/review` | Anonymous creation of a predefined synthetic run. `Idempotency-Key` 16–128 permitted ASCII characters. Body `{ "transferId": "TRF-1002" }`. 201 new / 200 exact retry. |
| POST `R/resolution-plans/preview` | `X-Demo-Capability` from review creation plus `Idempotency-Key`. Independently validates; 200 new or exact retry. |
| GET `P` | Public scoped plan and decision read; capability never returned. |
| POST `P/decision` | Capability plus exact plan version/hash, outcome and unverified review metadata. 200 recorded or exact retry. |
| POST `P/execute` | Capability plus exact plan version/hash. Requires decision. Atomic ledger/audit/state update; 200 or same result on retry. |
| GET `P/verify` | Public scoped independent verification against current records. |
| GET `P/audit` | Public scoped append-only plan audit. |

Creation returns the existing `runId`, `transferId`, `expiresAt` (Unix seconds), `fictionalDemo`, `evidenceMode`, plus **sensitive** `reviewCapability`. It is generated by `secrets.token_urlsafe(32)`, scoped to that run and retained for durable exact creation retries. Creation is no-store. Existing normal runs have no capability; changing creation mode under the same idempotency key is 409.

Private `POST /api/resolution-plans/preview`, `/{planId}/decision`, `/{planId}/execute` require `X-API-Key`, then return 503 `verified_review_not_configured`. They never treat a demo reference as authenticated approval. Demo routes reuse isolated run sessions only; there is no cross-scope lookup of private plans. Existing protected transfer audit routes remain unchanged.

## Preview

```json
{
  "transferId": "TRF-1002",
  "reconciliationRunId": "<actual latest reconciliation ID>",
  "agentInvestigationId": "<Flow correlation>:TransferInvestigationAgent",
  "investigationSummary": "<validated agent summary; untrusted narrative>",
  "overallRiskLevel": "MEDIUM",
  "documentEvidenceStatus": "NOT_PROCESSED_IXP_DISABLED",
  "proposedActions": [
    {
      "exceptionId": "<actual explained SEC-103 exception ID>",
      "securityId": "SEC-103",
      "disposition": "ACCEPT_VERIFIED_EXPLANATION",
      "evidenceReferences": ["<every actual exception evidence reference>"]
    },
    {
      "exceptionId": "<actual unresolved SEC-104 exception ID>",
      "securityId": "SEC-104",
      "disposition": "ESCALATE_TO_TRANSFER_OPERATIONS",
      "evidenceReferences": []
    }
  ]
}
```

Placeholders above are not fixture IDs or executable evidence. Every actual exception must appear exactly once. Security identity and evidence ownership must match. Acceptance requires EXPLAINED status and all matching verified corporate-action/mapping references. Unresolved shortages cannot be accepted. `OPEN_COST_BASIS_CASE` requires an unresolved cost-basis exception. `REQUEST_ADDITIONAL_EVIDENCE` and `ESCALATE_TO_TRANSFER_OPERATIONS` retain open exceptions. `REJECT_PROPOSED_PLAN` is a recognized disposition category but cannot be proposed as an executable action: select the REJECT review outcome instead, which applies no disposition rows.

Plan reads/mutation responses return `contractVersion=1.0`, `demoOnly=true`, `identityVerification=UNVERIFIED_DEMO_REFERENCE`, plan/transfer/reconciliation/investigation IDs, status, version/hash, actions, evidence, creation/update/expiry times, summary/risk/document status/client reference and optional `decision`. The hash covers the exact immutable content, data fingerprint and expiry. Versions are not caller-editable. `agentInvestigationId` is correlation metadata, not a claim of a UiPath job identifier.

## Decision and execution

```json
{
  "planVersion": 1,
  "planHash": "<64 lowercase hexadecimal characters from preview>",
  "reviewOutcome": "APPROVE",
  "reviewerReference": "<unverified demo reference>",
  "reviewerComments": "<optional, at most 2000 characters>",
  "additionalInformation": "<optional, at most 2000 characters>",
  "reviewEventReference": "<Flow correlation>:TransferOperationsReview"
}
```

Other outcomes: `REQUEST_EVIDENCE`, `ESCALATE`, `REJECT`. Reviewer and event references are 1–256 characters. A decision is immutable and unique per plan. Exact decision replay is idempotent; conflicting decisions and reusing an event for another plan return 409. Execute body contains only `planVersion` and `planHash`; no approval boolean or caller-supplied financial values are accepted. Execution never contacts external services inside a transaction.

## Verification and audit

Verification returns `transferId`, `reconciliationRunId`, `investigationSummary`, `planId`, `planStatus`, `humanReviewOutcome`, `evidenceReferences`, `reviewedDispositions`, `unresolvedExceptions`, `documentEvidenceStatus`, `verificationStatus`, `workflowOutcome`, `auditReference`, `auditEventIds`, `positionsUnchanged`, `transferCompleted=false`, `identityVerification`, `demoOnly=true`.

`VERIFIED_DEMO_STATE` requires a final plan state, a recorded decision, permitted dispositions matching persisted ledger entries, unchanged source/staging snapshots, unchanged current exception fingerprint and all required audit events. Otherwise the report is `NOT_VERIFIED` / `REVIEW_FAILED`; stale current data yields 409. It never means reviewer identity has been authenticated. The backend's `auditReference` is the plan ID; the final Flow report converts it to the scoped audit path.

Audit response: `{demoOnly, identityVerification, planId, items}`. Each item contains `auditEventId`, `transferId`, `planId`, `eventType`, `eventData`, `correlationId`, `timestamp`. Events: `PLAN_PREVIEWED`, `DEMO_REVIEW_RECORDED`, and either `DEMO_DISPOSITION_EXECUTED` or `DEMO_DISPOSITION_REJECTED`. Event data includes the demo/identity label, plan binding or effective actions as appropriate. Reviewer comments remain in the immutable decision record. Existing `audit_events` gains three nullable columns (`plan_id`, `event_data`, `correlation_id`), preserving prior rows/triggers.

## Errors, bounds and persistence

| HTTP | Examples |
|---|---|
| 401 | Missing/wrong private API key |
| 403 | Missing/wrong run capability; another run's capability |
| 404 | Unknown run, transfer/plan outside scope |
| 409 | Stale data/run, changed idempotency payload, binding mismatch, decision conflict/replay, decision required |
| 410 | Expired run |
| 413 | Oversized body (preview 32 KiB; decision 8 KiB; other demo POST 4 KiB) |
| 422 | Unsupported transfer, malformed contract, invalid exception/security/evidence/disposition |
| 429 | Public/creation budget or run/plan quota; inspect response and do not retry in a loop |
| 503 | Busy demo capacity or protected review not configured |

Existing creation budgets remain five per peer and twenty globally per minute, plus configurable public request limits and durable run quota/TTL. Plans are capped at five per run, actions at 100 and references at 30 per action. The one-worker lock serializes isolated operations. SQLite schema v3→v4 and registry v1→v2 are additive and idempotent; unexpected schemas fail without resetting storage. Decisions, disposition rows and audits are immutable in SQL as well as application code. Plan content is immutable; only permitted state transitions update it.
